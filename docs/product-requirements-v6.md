# 天气应用 MVP V6.0

> 产品定义：我想做一款以美国为主要市场的天气 App。真实天气提供日常价值，穿衣建议帮助更多人把天气用起来，跑步时间判断承担第一项专业场景验证。是否值得继续投入，要看人们会不会依据建议处理真实安排，并持续回来使用。

体验入口：[天气应用](https://dodgey512-blake.github.io/weather-v1/)；[VIS 2.0 设计与组件](https://dodgey512-blake.github.io/weather-v1/vis-2/)；[设计 Skill 下载](https://dodgey512-blake.github.io/weather-v1/vis-2/downloads/weather-design-skill.zip)。

安装与开发：[Android 体验包](https://dodgey512-blake.github.io/weather-v1/downloads/Weather-V1.0.apk)；[Android Studio 工程](https://dodgey512-blake.github.io/weather-v1/downloads/Weather-V1.0-AndroidStudio.zip)。交付链接以实际发布验收为准。

## 1. 产品定位：天气是主入口，专业价值落在具体安排

我希望用户打开后，首先觉得这是一款有品质的天气产品。跑步有一定深度，但只占个人生活中的一个场景，不能把整款产品做成训练工具。

1. 第一层价值是看懂天气：地点、当地时间、当前天气、未来变化、官方预警和数据是否有效，打开即能理解。
2. 第二层是日常使用：今天穿什么、是否带外套和雨具、早晚温差大不大。这部分保持免费，让不跑步的人也有打开理由。
3. 第三层是具体安排：用户本来就准备跑步，天气帮助比较整段训练是否有明显冲突，允许范围内是否存在更好的时间。
   1. 计划由用户提出；我不自动编造训练，也不代替教练调整强度。
   2. 建议说明原因、依据和有效期，最后由用户决定。
   3. 后续可以向其他生活方向展开，但每个方向都需要独立验证，不把模块数量当成产品价值。

产品工作名暂用“天气 Weather”。正式品牌与商标仍待确认；演示页面不使用虚构用户身份、头像或服务规模来增加可信感。

## 2. 用户与核心假设

1. 日常用户希望快速知道当地天气和出门准备，不愿意阅读过多参数。天气首页和 OOTD Lite 需要独立成立。
2. 第一批专业场景用户是美国城市跑者：本来有安排，会因为降雨、雷暴、高温、风或空气质量改变时间，目前需要自己对着预报作判断。
3. 我会先集中观察 Austin 的真实计划，再考虑 Seattle、New York、Denver 等不同气候场景。全美地点可查询，不等于已经完成全美适用性验证。
4. 核心假设有三项：
   1. 用户愿意输入一次真实计划，而不只是看看示例。
   2. 用户理解判断依据，并愿意明确选择接受、保留或自行修改。
   3. 训练前的天气变化检查和训练后的结果回看，能够形成持续价值。
5. 目前还没有美国用户研究、留存和真实付费结果证明这些假设。首次测试考虑招募 5—8 名目标用户，记录独立完成情况、疑问和最终决定（待招募）。

如果用户仍然需要演示者解释才能完成计划，或者建议与个人经验经常矛盾，应优先研究原因，不能用增加功能掩盖问题。

## 3. 产品范围

第一轮保留一条清楚的使用路径：选择地点、看天气、添加计划、理解判断、作出决定、查看变化、记录结果。

1. 免费能力包括完整天气入口、未来 72 小时详情、官方预警、日常穿衣和一条待执行跑步计划；已经结束的计划可以保留记录。
2. 跑步判断只比较时间，不自动修改路线、配速、训练负荷或比赛目标。训练类型用于记录，备注不参与自动判断，界面需要说明。
3. 用户可以导出日历文件自行导入，但不会出现已经写入 Apple Calendar、Garmin、Strava 或手表的提示。
4. 产品包含价格意向页面，记录对后续专业权益的态度；不接收费、不创建订阅、不用选择意向模拟购买成功。
5. 暂不纳入数字衣橱、电商交易、第二专业模块、完整训练课程、账号体系和跨设备同步。iOS 原生应用、后台远程推送和商用服务端属于后续生产工作。

主导航只有“天气、计划、设置”三个 Tab。天气承担日常入口，计划保留当前安排和历史结果，设置集中处理偏好、来源、提醒与数据。用户不会在首页被要求挑选一长串付费模块。

## 5. 地点、语言与时间

1. 用户可以搜索美国城市，也可以在点击“使用当前位置”以后申请定位。首次打开不主动弹定位或通知权限。
   1. 搜索结果区分州和时区，避免同名城市误选。
   2. 先选中地点，再由底部操作确认；搜索失败可以重试或选择常用城市。
   3. 定位拒绝、超时或位于暂不支持地区时，手动搜索始终可用。
2. 当前浏览城市与计划地点分别保存。人在上海查看 New York 天气，或者从 Austin 切换到 Seattle，都不能静默改变既有计划。
3. 界面默认简体中文，设置中可切换英文。导航、字段、验证、状态、通知和辅助名称需要一起变化；用户自由输入和官方预警原文保留原内容。
4. 语言、单位和时区独立：
   1. 切英文不自动改成华氏度，也不移动计划时间。
   2. 单位提供公制和美制；内部保存统一物理量，展示时转换。
   3. 天气日期、训练时间和消息时间按对应地点时区显示，不能依赖手机所在时区推算。
5. 开始时间使用绝对时间保存。遇到夏令时切换，重复时间需要明确选择第一次或第二次，不存在的时间要求重新选择，不能替用户静默修正。

## 6. 天气首页

我希望首页在没有跑步计划时仍然值得使用。当前天气和未来变化要比宣传语更醒目，天气动画不能挤占阅读空间。

1. 顶部放地点、刷新和消息入口。有效官方预警优先出现，展示入口与影响时间；不能因为普通天气卡片更好看而把预警压到后面。
2. 天气主体展示当地日期时间、天气类别、温度、体感、风、可解释的高低温口径和来源状态。缺少体感或风时明确缺失或不展示该数值，不拿气温或零值冒充。
3. 逐小时区提供接下来天气的快速扫描，完整 24 小时趋势和未来 72 小时进入详情，按当地日期分组。点击日概览可以进入对应日期的小时视图。
4. 温度曲线、降水概率和训练区间来自真实时间序列。缺失值应当断开或标记，不绘制装饰曲线充当证据；降水概率不等于降雨强度。
5. 当天重点区突出风、降水或 AQI。AQI 要带模型来源说明，不能与当地地面监测混淆。
6. OOTD Lite 与下一次跑步位于生活内容层。没有计划只显示添加入口；有计划展示真实地点和时间，不能生成虚构冲突来诱导点击。
7. 当日高低温采用明确的日级口径。演示依可获得的当天预报计算时，需要说明范围，不能被理解为已经测得的全天极值。

## 7. 数据状态与来源

我会把“来自哪里”“何时产生”“是否还能使用”分开表达。刚刚请求成功，不代表天气刚刚观测。

| 展示状态 | 用户看到什么 | 判断与操作 |
|---|---|---|
| 最新 | 真实来源及原始数据时间 | 在有效期内正常阅读与决定 |
| 有效缓存 | 已缓存，并保留原发行、观测和获取时间 | 数据仍有效时可以使用，不伪装成新观测 |
| 部分可用 | 哪个来源缺失，哪些内容仍可阅读 | 逐项判断条件；不能因为实况失败就清空完整预报 |
| 已过期 | 旧内容和失效时间，提供刷新 | 暂停应用过期建议 |
| 暂无数据 | 缺失字段与恢复入口 | 不以零值或合成天气补成“正常” |
| 情景演练 | 全程显示独立演练标识 | 只在演练范围内运行，不写真实计划和指标 |

1. 天气实况、逐小时和官方预警使用 [NWS 公开接口](https://www.weather.gov/documentation/services-web-api)。每一类请求独立处理失败，普通观测失败不应覆盖成功取得的预警。
2. 地点搜索使用 [Open-Meteo Geocoding](https://open-meteo.com/en/docs/geocoding-api)，结果过滤美国地区，再解析 NWS 地点与时区。GPS 坐标仅在用户授权后取得。
3. AQI 使用 [Open-Meteo Air Quality](https://open-meteo.com/en/docs/air-quality-api) 提供的 CAMS 模型数据。页面写明模型估计，并非 AirNow 地面实测；缺少覆盖时提示自行确认户外条件。
4. 内部温度为 °C，风速为 km/h，概率为 0—100 或缺失；按供应商 unitCode 转换。未知单位保留缺失，风向缺失时不假装有精确方向。
5. 来源页面分别显示预报发行、观测、预警检查、模型有效时间，以及实际获取和到期时间。快照保存来源状态、地点、时间与标识，供某次判断回看。
6. 当前演示的有效期包括：预报获取后约一小时且受原始发行时间限制，实况观测约 90 分钟，预警检查约五分钟，AQI 模型有效时刻后约两小时。这些是实验参数，生产阶段仍需结合实际源更新频率校准。
7. 公开接口存在超时、限流和覆盖差异。商业生产需要落实许可、服务端缓存、监控与支持责任，不能把“可以免费调用”写成服务保证。

## 8. 日常穿衣

OOTD Lite 是免费日常能力。我只希望它减少出门准备的判断，不把它发展成衣橱或购物产品。

1. 输入包括有效温度或体感、降水、风、当天温差、冷热偏好和日常场合。没有有效数据时显示等待刷新，不生成确定的穿衣结论。
2. 输出控制在衣物层数、可脱卸外套、雨具、防滑鞋和防晒类别。雷暴等天气先提醒调整户外安排，不能把穿雨衣当成解决天气风险。
3. 用户可选择日常、通勤工作或户外活动；冷热反馈保存在本机，并用于轻量调整后续衣物层数。
4. 首页摘要与详情使用同一个建议模型。用户不应在首页看到“带雨具”，进入详情却只有不相关的防晒建议。
5. 这里的偏好调整是透明规则，不声称已经学出个人预测模型。穿衣查看与反馈单独记录，不用于证明跑步专业价值成立。

## 9. 跑步计划

1. 第一屏只保留地点、开始时间、预计时长、可调整范围。预计时长用于完整暴露窗口，不能只显示在卡片上。
2. 未来 72 小时按绝对时间判断，开始不能已过去，整段结束不能超过承诺范围和数据覆盖。输入需要清楚提示具体哪项有问题。
3. 可调整范围提供固定、前后 30 分钟、前后 1 小时、前后 2 小时。固定时间不生成改期；候选时段必须满足允许范围及完整预报覆盖。
4. 室内替代开关参与“没有可用户外窗口”的分支。训练类型和备注放到选填区域，注明用途，避免多填信息却没有任何实际影响。
5. 表单草稿在本机保存；保存失败保留输入，不先提示成功再让数据丢失。关键输入修改以后，旧判断与旧决定失效，重新计算。
6. 一次只保留一条待执行计划。已完成、已取消和待执行分开，结束的计划不继续显示为下一次跑步，也不继续自动天气检查。
7. 取消保留历史；删除需要明确确认并提示结果。生产验收还要确认误删恢复策略。用户可以导出 ICS 文件自行导入日历，产品不声称自动同步外部账号。

## 10. 判断规则

我希望专业性体现在依据清楚、约束被尊重，而不是给出更多看似专业的分数。

1. 先验证计划、地点、数据覆盖、来源新鲜度和官方预警状态，再分析开始至结束的全部小时；缺最后一段预报，也不能以第一小时替代。
2. 原时段没有明显影响时允许保留；有关注因素但没有明显更好的窗口时提示准备与留意；存在明显更好的完整时段时才给改期。
3. 整个允许范围都有雷暴或相关预警时，明确显示没有可用户外窗口。没有更好的时间，不等于可以挑一个稍早但同样有风险的时间。
4. 预警按所在地、生效结束区间、等级与训练时段匹配。当前已发布但在训练前结束的预警，不能无差别影响所有未来计划；未知严重度也不能当成正常。
5. AQI 需要覆盖完整训练窗口。缺失时保留不确定性，不用“空气良好”补齐；模型 AQI 较高时提示重新考虑户外安排，不给个人医疗判断。
6. 候选开始时间按 15 分钟步长比较。完整时段的温度、降水、风和 AQI 共同参与内部排序；只有原时段确有影响、候选不含不可用条件且排序改善达到实验阈值，才给改期。

| 实验信号 | 当前基线 | 产品表达 |
|---|---|---|
| 高温 / 体感热 | 30°C / 32°C | 比较更低热暴露时段，说明温度与体感来源 |
| 低温 | 0°C | 提示低温因素，不自动调整训练强度 |
| 风 / 阵风 | 35 / 50 km/h | 展示整段最大值；数据缺失不按平静处理 |
| 降水概率 | 50% | 提示较高可能性，不描述成一定下雨 |
| 雷暴、雪冰、相关官方预警 | 完整时段内存在 | 优先判断户外窗口是否可用 |
| 数据或覆盖不足 | 任一必要条件缺失 | 暂停确定性建议，提供刷新或编辑入口 |

以上阈值属于 `experimental-1.0` 产品实验规则，尚未经美国跑者研究验证，不是官方安全分。规则还包含更高风、热暴露和 AQI 等不可用窗口条件，具体值应在来源页面与实现契约保持一致。

1. 当前更高风险条件包括风速达到 50 km/h、阵风达到 70 km/h、气温达到 36°C、体感达到 40°C 或模型 AQI 高于 150；AQI 高于 100 已进入关注因素。
2. 当前内部排序为降水概率 × 0.4、最大风速 × 0.7、超过 26°C 的温差 × 4、低于 5°C 的温差 × 3，以及 AQI 超过 50 的部分 × 0.5；不可用天气与相关预警另加权处理。改期要求候选至少改善 10 个内部单位。这些单位不对用户包装成安全概率。
3. 雷暴、雪冰和相关预警采用保守处理，不能因为普通排序较低就恢复为可用窗口。以上参数需要通过实际场景和目标用户研究继续验证，不能只用界面体验判断合理性。

每条判断展示原计划、完整训练区间、主要因素、建议时间、来源、发行时间、有效期和保留入口。用户看到的曲线与数值必须能对应同一快照。

## 11. 决定与后续变化

1. 用户可接受改期、保留原时间或自行编辑。没有户外窗口且允许室内替代时，可记录室内选择，并取消对应户外安排。
2. 接受前再次核对计划更新时间、快照标识、规则版本、有效期和候选时段。确认层打开后天气已变化，应该返回新判断，不继续应用旧值。
3. 更新成功只表示应用内计划保存成功。页面同时保留修改前后时间和决定记录，不能把本机保存包装成日历、手表或支付成功。
4. 监测开启时，应用在前台定期检查计划地点；回到前台或网络恢复时可以刷新。当前演示不承诺关闭应用后仍持续检查，也没有后台远程推送服务。
5. 消息来自新旧快照的实际比较，包括判断类别、候选窗口、降水或温度的重要变化，以及预警更新。概率和快照时间用真实值，不固定填写“88%”。
6. 用户可按需申请系统通知。不支持或拒绝授权时仍能查看应用内消息；已授权也不把通知生成等同于系统一定送达。
7. 打开变化消息以当前判断为准。原计划已结束或不是当前计划时，应进入对应记录，而不是误展示另一条计划的结论。

## 12. 反馈与数据记录

训练结束后才邀请反馈。我关心实际发生了什么，而不是收集一份默认全是正向的问卷。

1. 完成情况、实际体感、建议是否有帮助，初始都不替用户选择。未填完整时提示缺项，保存后可以回看和修改。
2. 反馈关联计划；决定关联建议、规则与快照。完成和取消会结束对应监测，不让旧计划持续占用首页。
3. 本机事件包括 `weather_loaded`、`plan_created`、`plan_edited`、`recommendation_viewed`、`recommendation_decided`、`weather_change_opened`、`outcome_saved`、`ootd_viewed`、`ootd_feedback`、`pricing_intent` 等。保存事件需要带计划或快照标识及必要上下文。
4. 当前演示把记录保存在本机，通过 JSON 导出供观察，不具有中央采集后台。事件保留容量有限，不能把它描述成已经具备长期全量分析能力。
5. 核心指标关注“看过有效判断的真实计划中，作出明确决定的比例”，再观察实际执行和建议帮助情况；浏览天气、穿衣点击和报价意向单独计算。
6. 正式实验还需要把去重、曝光与决定口径、数据保留、匿名采集授权和失败补报确定下来（待外部测试方案）。

## 13. 商业化：先验证付费意向，真实收入另行检验

我考虑让专业权益围绕多计划、持续监测、历史结果和经过验证的个体化展开，天气基础能力及官方预警继续免费。

1. 报价实验暂定月付 $2.99、年付 $19.99。用户可选“愿意按这个价格试用”或“目前不考虑”，并可重新选择。
2. 页面明确这是拟定价格和后续权益。点击不收费、不开订阅、不解锁未交付功能；记录仅保存在本机，可导出研究。
3. 意向不等于购买。用户愿意尝试，也不等于已经证明价格、续费或收入成立。
4. 真正收费前，需要确认建议持续有用、权益可以交付，再落实平台购买、取消、失败、恢复和到期状态。当前没有把这些生产工作写成已经完成。

## 14. 视觉、动态与无障碍

1. VIS 2.0 使用夜蓝、暖白、天空蓝、荧光绿和风险色；中文与功能正文使用系统字体，温度与少量展示标题使用 Space Grotesk。正文 16—17、辅助 14—15、标签至少 12 CSS px。
2. 玻璃材质用于导航、工具栏和浮层控制，内容卡、预警和表单保持清楚阅读面。Web 通过模糊、边缘光与有限弹性近似 Liquid Glass，不声称与原生 iOS 光学效果相同。
3. Tab 的已选页面、拖动候选和活动状态分开。按住、移动、松手、取消、快速反向与页面中断后需要正确归位；切换语言时不遗留半途选中状态。
4. 晴昼、晴夜、云、雨、雷暴、雪、雾、风及未知状态分别表达。夜间不画太阳；降雨为闭合水滴，可有前后层与有限风角，缺少风向或雨强时不声称精确对应实况。
5. 按压约 120ms、控件状态约 200ms、页面过渡约 320ms。持续动画位于信息后方，静止导航不摆动；减少动态或关闭动效后，保留可辨认的静态天气。
6. 顶部、独立滚动内容、底部 CTA 与 Tab 需要在短屏、横屏和键盘展开时保持可用。手机网页不重复绘制假系统时间或刘海。
7. 所有操作命中区至少 44×44 CSS px；状态同时使用文字、图形和颜色。图标有辅助名称，页面切换提供合理焦点，弹层支持返回和关闭。
8. 深浅色、系统主题、减少透明度、放大文字和屏幕阅读器分别验收。真实手机 Safari、低端 Android 性能及原生辅助功能仍需设备级验证，不能拿桌面截图替代。

## 15. 交付形态与隐私

1. 浏览器版以公开 URL 使用，支持移动端响应式与 PWA 外壳。首次加载和实时数据仍需要网络；缓存界面资源不等于离线拥有最新天气。
2. Android 体验包是 Android Studio 工程内的 WebView 混合应用：本地内置网页资源，系统层连接定位、通知权限和文件保存，并处理返回与安全区域。它不是原生 SwiftUI 应用，也不代表 iOS 已上架。
3. 原生桥只向应用受控来源开放；外部资料链接通过外部浏览器打开，不能让任意远程页面调用本机能力。APK 与工程用于测试和继续开发，商店发布签名与审核单独完成。
4. 当前没有账户、云端个人档案或跨设备同步。计划、偏好、消息、反馈、事件和天气缓存保存在当前浏览器或安装应用中，二者存储各自独立。
5. 查询天气会把所选地点坐标发给供应商，搜索会发送搜索词；GPS 只有主动使用并授权以后才获取。位置不被包装成默认必需权限。
6. 设置提供本机 JSON 导出和确认重置。读取异常应提示并尽量保留原记录，保存失败不清空输入；下载需要由平台实际保存结果反馈，不能凭按钮点击声称文件已存在。
7. 原型不接广告，也没有中央行为数据上传。后续增加账号、远程推送或分析平台时，需要重新定义隐私披露、保留周期、删除和权限，而不是沿用“仅本机”的描述。

## 16. 验收与下一步

我会分别验收“产品流程能够独立使用”与“可以承担商业生产”。前者通过，并不能自动宣布后者完成。

| 验收项 | 必须达到的结果 |
|---|---|
| 地点与时间 | 搜索/定位拒绝均能继续；纽约计划不被上海设备或浏览城市改变；DST 不静默修正 |
| 数据 | 新鲜、缓存、部分、过期、缺失与情景不混淆；保留原时间；未知单位与空值不按零处理 |
| 判断 | Fixed 不改期；完整时长跨小时和午夜；缺任一段预报暂停；全窗口雷暴不给虚构最优时间 |
| 决定 | 变更前重新校验；保存失败保留输入；编辑使旧结果失效；结束计划退出当前监测 |
| 后续使用 | 消息有实际快照依据；通知按需；反馈中性；报价不会触发支付 |
| 界面与动效 | 320/375/390px、短屏、横屏、键盘、大字号可操作；雨滴明确；昼夜正确；关闭透明/动态仍可用 |
| 语言与记录 | 中英文状态一致切换；时区单位独立；数据能实际导出，重置有明确确认 |
| 交付 | 公网匿名可开；组件画布、SVG、Skill ZIP、APK 与工程包真实存在且可下载使用 |

1. 规则测试需要覆盖时长、固定、无窗口、边界、地点、单位、预警交集、缺失、缓存、失效与 DST；接口测试还需验证某个来源失败不会破坏其他来源。
2. 可用性测试重点观察首次计划完成、判断理解、保留或改期，以及训练后的实际反馈。不同背景用户的误解在哪里，需要访谈材料支持，不能由内部走查代替。
3. 商业生产仍需自有服务端、供应商商业许可、源更新与调用量监控、错误告警、中央实验采集方案、后台远程推送、购买体系，以及平台真机验收。模型 AQI 和规则阈值也需要覆盖地区验证。
4. Android 模拟器已通过 8 项功能检查，并在实际 WebView 中验证中英文切换。本机模拟器系统层出现过 ANR 弹窗，整体流畅度与真机表现尚未验收；WebView 内容截图只证明应用页面实际渲染，不能替代整机体验证据。
5. 可能的思路探讨：先把一条真实计划的判断稳定性和复用意愿验证清楚，再讨论扩大计划数量、丰富天气能力和增加专业方向。是否继续，依据真实使用结果决定。
